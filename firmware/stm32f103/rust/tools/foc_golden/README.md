# FOC golden-vector recorder

`foc_golden_left.csv` is generated by the **unmodified** pinned Simulink
controller in `firmware/stm32f103/eferu-foc/eferu`. It is the reference for the Rust FOC
port; do not hand-edit it.

Regenerate from the project root:

```sh
INC=firmware/stm32f103/eferu-foc/eferu/Inc
SRC=firmware/stm32f103/eferu-foc/eferu/Src
OUT=firmware/stm32f103/rust/tools/foc_golden
clang -std=gnu99 -O1 -I"$INC" -include "$OUT/host_limits.h" \
  "$OUT/harness.c" "$SRC/BLDC_controller.c" "$SRC/BLDC_controller_data.c" \
  -o "$OUT/foc_harness" -lm
"$OUT/foc_harness" > "$OUT/foc_golden_left.csv"
rm "$OUT/foc_harness"
```

`host_limits.h` exists only because the generated source rejects LP64 hosts;
it defines the 32-bit `long` limits the source expects without touching the
reference. The harness applies the pinned jbot limits (`i_max = 8000`,
`n_max = 6400`, `z_ctrlModReq = TRQ_MODE`) and feeds a deterministic hall and
current sequence for 120 ticks, which covers all three scheduler tracks.

`foc_golden_right.csv` is the matching right-motor trace (`z_selPhaCurMeasABC =
1`), recorded with `harness_right.c`, which is identical to `harness.c` except
for the phase-selection argument:

```sh
clang -std=gnu99 -O1 -I"$INC" -include "$OUT/host_limits.h" \
  "$OUT/harness_right.c" "$SRC/BLDC_controller.c" "$SRC/BLDC_controller_data.c" \
  -o "$OUT/foc_harness_right" -lm
"$OUT/foc_harness_right" > "$OUT/foc_golden_right.csv"
rm "$OUT/foc_harness_right"
```

`f103_core/src/foc_generated.rs` replays both CSVs in host tests and asserts all
eight outputs exactly, with no tolerance. The module is declared in
`f103_core/src/lib.rs` and is wired into the firmware ISR, but the controller is
held in OPEN mode until the safety state is armed and MOE stays low; bench and
Safety-Reviewer approval are still required before any gate drive is enabled.

Run the golden regression with:

```sh
cd firmware/stm32f103/rust && cargo test -p f103_core foc_generated
```
